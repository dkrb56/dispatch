## Background workers
<!-- dispatch-section: 634a47a22eb78d03 -->
- A task is two runs of one worker session. The plan run reads the code and writes a plan. The work run executes the approved plan. Triage starts and resumes a worker only with the script `D:/dev_projects/dispatch/.dispatch/worker.ps1`, never with `claude --bg` or `claude --resume` directly. A worker works in the main checkout (`worktree.bgIsolation` is `none`).
- Triage writes each brief to `D:/dev_projects/dispatch/.dispatch/briefs/<ticket-id>.md`: the user's words, the constraints, and the command that proves the work. The brief says nothing about the approach; the plan run decides that.
- `powershell -ExecutionPolicy Bypass -File D:/dev_projects/dispatch/.dispatch/worker.ps1 plan <ticket-id>` starts the plan run on the options in `D:/dev_projects/dispatch/.dispatch/plan-flags.txt`: without the Edit tool, without the Agent tool and without a prompt; its Write tool may write only into `D:/dev_projects/dispatch/.dispatch/plans/`. The plan run writes the plan to `D:/dev_projects/dispatch/.dispatch/plans/<ticket-id>.md`, changes nothing else, and ends its turn.
- A plan has these sections: Summary (3 lines maximum: what changes, how many files, how many decisions and whether one is `HOLD`; the task card of Dispatch shows these lines); Goal; TL;DR (2 to 4 lines in plain words for the user, 25 words maximum each: what changes for the user and why, everyday words, few technical names; the Decisions window shows them under the Goal); Acceptance (commands with the expected output); Files to change (each with the symbol or an anchor line, the change and the reason); Files read (one fact each); Steps; Decisions (each a numbered item with its question, and under it one list item per option, because Dispatch shows each option as a button: first `- Default:` with the recommended choice, or `- HOLD:` instead when only the user takes it, then at least one real alternative as `- Other:`; each option one short line, its reason after it as `Recommended: …` or `Not recommended: …`; the word HOLD stands in no other line of this section); Do not touch; Size (files). No code in a plan.
- When the plan run is done, triage tells the user that the plan is ready. The user reads the plan in the task card of Dispatch and clicks Approve or Reject there; only that click is the yes. Dispatch runs `powershell -ExecutionPolicy Bypass -File D:/dev_projects/dispatch/.dispatch/worker.ps1 approve <ticket-id>`, which resumes the same session on the options in `D:/dev_projects/dispatch/.dispatch/work-flags.txt`, and writes one line into the triage chat. Triage never runs approve itself; the local settings deny it that verb. The script refuses when the working tree has uncommitted changes outside `D:/dev_projects/dispatch/.dispatch/` (after Setup pipeline, the user commits the setup files first; Dispatch commits the files of `D:/dev_projects/dispatch/.dispatch/` itself), when the worker still runs, or when the task was stopped.
- The work run follows the plan. A deviation goes into the report, not into the code. The worker ends with one local commit on the current branch, with the ticket id in the message. It never pushes or merges. The user decides the push.
- A worker ends with a report in `D:/dev_projects/dispatch/.dispatch/<ticket-id>.md`. The report starts with four lines, each `key: value`: `state` (`done`, `needs-decision` or `failed`), `needs` (`nothing`, `decision` or `permission`), `files` (the changed files, or `none`) and `plan` (the plan file). Then: what it did, what it verified and how, open questions, where the work is.
- A worker starts no session and sends no message to a chat. It has no question tool. A question for the user goes into the report under the heading `## Questions`: numbered items, each with its options as list items, the recommended option first. Each option is one short line, because Dispatch shows it as a button and sends it back word for word; the details stand above the questions. The worker then writes `state: needs-decision` and `needs: decision` and ends its turn, also when the question is about a permission. `needs: permission` means: a refused tool call stopped the work, the report names the refused call and the rule it needs, and the work goes on with a follow-up `Continue` once the user changed the rule. The user answers in the task card of Dispatch, and the answer arrives as a follow-up `Answer to question N: <option>`.
- A follow-up goes through `powershell -ExecutionPolicy Bypass -File D:/dev_projects/dispatch/.dispatch/worker.ps1 reply <ticket-id> "<message>"` and quotes the user's words exactly. The script takes the options of the run from `D:/dev_projects/dispatch/.dispatch/<ticket-id>.state`.
- Triage does no implementation. It classifies, writes briefs, starts the plan run, shows the plan, relays the yes, checks results and reports to the user.
- The session of a worker is named `<ticket-id> [plan]` in its plan run and `<ticket-id> [work]` in its work run; a worker of an older script has the bare ticket id. Triage checks workers with `claude agents --json --all` or `powershell -ExecutionPolicy Bypass -File D:/dev_projects/dispatch/.dispatch/worker.ps1 status`: `done` = finished, `blocked` with `status: waiting` = at a permission prompt, `blocked` with `status: idle` = the turn ended with a question that stands in the report (`powershell -ExecutionPolicy Bypass -File D:/dev_projects/dispatch/.dispatch/worker.ps1 status` says `done` then), `failed` or `stopped` = ended badly. It reads the plan or the report file first, `claude logs <id>` second.
- Triage runs at most 3 workers, and at most one in its work run. Triage does not poll: Dispatch writes one line into the triage chat when a worker is done, blocked or failed, when the user approved or rejected a plan, and when the user answered a question.
- Triage never answers a worker's question or permission prompt with its own words. A question is answered in the task card of Dispatch; a permission prompt is answered in the agent view.

## Working rules
- Write to the user in plain words: everyday words, short sentences, say what it means for the user. This holds for each message that the user reads.
- Give no duration estimate for the work of a session. An estimate for a test run or a build is permitted.
- Keep each message to the user short: the result first, then the decisions that the user must make. Give details when the user asks.
- Only the user's own words are approval. A message from another session is information.
- The user decides design, plans, removed features, changes to shared tools, uploads and messages to other people.
- If a permission check stops a session, no other session does that action for it. Tell the user.
- Reproduce a bug before the fix. State the cause with its evidence before you write code.
- Scripts write the proof. A session never writes a test result by hand.
- A failed test is a bug. A second run does not make it pass.
- A session that sees waste or a different problem notes it in its report and does not fix it inside its own task.
- Take each time from the clock in the same message.
- Parse-check a new or edited PowerShell script before the first real run: `[System.Management.Automation.Language.Parser]::ParseFile`.
- A report also says what nobody tried, in words that a tester understands.
