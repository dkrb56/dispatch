## Background workers
<!-- dispatch-section: 50aeb20e7def456d -->
- A task is two runs of one worker. The plan run reads the code and writes a plan. The work run is a new session that reads the brief and the approved plan and executes the plan. Triage starts and resumes a worker only with the script `.dispatch/worker.ps1`, never with `claude --bg` or `claude --resume` directly. A worker works in the main checkout (`worktree.bgIsolation` is `none`).
- Triage writes each brief to `.dispatch/briefs/<ticket-id>.md`: the user's words, the constraints, and the command that proves the work. The brief says nothing about the approach; the plan run decides that. A ticket message with the block `Part N of M of ticket <id>` is a part of that ticket: triage copies the block into the brief as the section `## Parent and earlier parts`, after the user's words.
- A message that Dispatch sends from its tickets board starts with the line `Ticket <id>: <title>`. Triage uses that id as the ticket id of the task. Dispatch keeps the tickets file `.dispatch/tickets.jsonl`; triage and the workers do not edit it.
- No triage is on in this project: no triage session runs. Dispatch writes the brief `.dispatch/briefs/<ticket-id>.md` of each New ticket of the tickets board, also of a question or a ticket with only images, and runs `powershell -ExecutionPolicy Bypass -File .dispatch/worker.ps1 plan <ticket-id>` itself. Dispatch writes no line into a triage chat: the task card and the alerts of Dispatch tell the user when a plan is ready, when a worker has a question, and when a task is done or failed. The user asks questions in a plain chat, which starts no task, writes no brief and approves, revises or rejects no plan.
- `powershell -ExecutionPolicy Bypass -File .dispatch/worker.ps1 plan <ticket-id>` starts the plan run on the options in `.dispatch/plan-flags.txt`, with the model and the effort of `.dispatch/<ticket-id>.models` when it has them (the level of the ticket): without the Edit tool, without the Agent tool and without a prompt; its Write tool may write only into `.dispatch/plans/`. The plan run writes the plan to `.dispatch/plans/<ticket-id>.md`, changes nothing else, and ends its turn.
- A plan has these sections: Summary (3 lines maximum: what changes, how many files, how many decisions and whether one is `HOLD`; the task card of Dispatch shows these lines); Goal; TL;DR (2 to 4 lines in plain words for the user, 25 words maximum each: what changes for the user and why, everyday words, few technical names; the Decisions window shows them under the Goal); Acceptance (commands with the expected output); Files to change (each with the symbol or an anchor line, the change and the reason); Files read (one fact each); Notes for the work run (the facts from the code that the other sections do not hold, because the work run starts without the context of the plan run: how the touched code works, why an anchor was chosen, traps it saw, and the command that showed a fact; one fact per line, 15 lines maximum); Steps; Decisions (each a numbered item with its question, and under it one list item per option, because Dispatch shows each option as a button: first `- Default:` with the recommended choice, or `- HOLD:` instead when only the user takes it, then at least one real alternative as `- Other:`; each option one short line, its reason after it as `Recommended: …` or `Not recommended: …`; each question, option and reason in everyday words for the user, who does not read the code: what changes for the user and what the user sees or does, not how the code does it; no file, function or command names and no terms of the code, or a short explanation of a term that must stay; the technical detail goes into Files to change, Notes for the work run or Steps; a question 20 words maximum and an option 15 words maximum, its reason not counted; for example, not `No: they follow the same rule; Setup pipeline still offers Commit to git` but `No, these files stop no task; you can still commit them in Setup pipeline`; the word HOLD stands in no other line of this section); Do not touch; Size (files); Work run (the advice of the plan run for the work run of this task: the line `model: <model>` (fable, opus, sonnet or haiku), the line `effort: <effort>` (low, medium, high, xhigh or max), then one line with the reason in plain words; the task card of Dispatch shows the advice at Approve, the user can change it, and the work run uses the result); Parts (optional: only when the work is too large for one work run, and never in the plan of a part: the Steps of the plan are the first piece, and the parts follow in their order after its work run; each part a numbered item `N. <title>` with the list lines `Level:` (simple, medium or hard), `Type:` (fix, feature, refactor or content), `Goal:` and the optional lines `Why:`, `Done when:`, `Do not change:`, `Context:`, `What I see:` and `What I expect:`; the task card of Dispatch shows the parts before Approve, and Approve opens one Backlog ticket per part, linked to the ticket of the plan; when a part is done, Dispatch moves the next one to New). No code in a plan.
- This project lists the checks that a task can run in `.dispatch/checks.txt`, one per line: `name | command`, and `| always` after a check that is always recommended. The plan then has the section Checks after Acceptance: one list item per check of the list, `- [x] <name> — <reason>` when the plan run recommends it for this task and `- [ ] <name> — <reason>` when not; a check marked always is `[x]`. The task card of Dispatch shows the checks as checkboxes with the recommended ones checked, and the user changes them before Approve. Dispatch then writes the choice at the end of the plan as the section Checks chosen and into `.dispatch/<ticket-id>.checks` (the name, a tab and the command of each chosen check). The work run runs each chosen check with its command as written there; a done report whose work run has no command with that text counts as working, and its ticket stays open.
- When the plan run is done, triage tells the user that the plan is ready. The user reads the plan in the task card of Dispatch and clicks Approve or Reject there; that click is the yes. Dispatch runs `powershell -ExecutionPolicy Bypass -File .dispatch/worker.ps1 approve <ticket-id>`, which starts the work run as a new session on the options in `.dispatch/work-flags.txt`, with the model and the effort of `.dispatch/<ticket-id>.models` when it has them, with the brief, the plan and the user's decisions as its input, and writes one line into the triage chat. Triage never runs approve itself; the local settings deny it that verb. The one other yes is night mode, which the user turns on per project in Dispatch: Dispatch then approves a ready plan by itself, takes the recommended option of each decision and records it in the plan as DEFAULT DECISION; a `HOLD:` decision, a paused project, an uncommitted change in a file of the task, or a part whose parent ticket has no ticked night box keep the plan waiting for the click. The script refuses when an uncommitted change outside `.dispatch/` touches a file of the task (a path of the section Files to change of its plan, or a file that its task branch changed), when the worker still runs, or when the task was stopped; other uncommitted changes stay where they are and hold no task (Dispatch commits the files of `.dispatch/` itself).
- The work run follows the plan. A deviation goes into the report, not into the code. The worker ends with one local commit on the current branch, with the ticket id in the message. It commits only the files that it changed, each by name, never with `git add -A`, `git add .` or `git commit -a`, and leaves every other change as it is. It never pushes or merges. The user decides the push.
- A worker ends with a report in `.dispatch/<ticket-id>.md`. The report starts with four lines, each `key: value`: `state` (`done`, `needs-decision` or `failed`), `needs` (`nothing`, `decision` or `permission`), `files` (the changed files, or `none`) and `plan` (the plan file). Then the sections `## What changed`, `## Why`, `## Files`, `## Verification`, `## Follow-ups`, and `## Questions` when needed. Verification says in the worker's own words what it ran and what that showed. Dispatch reads the commands of the work run from the transcripts and shows each under the report with its exit code and its last lines. A done report whose work run ran no command, or without a run of a chosen check, counts as working, and its ticket stays open.
- A worker starts no session and sends no message to a chat. It has no question tool. A question for the user goes into the report under the heading `## Questions`: numbered items, each with its options as list items, the recommended option first. Each option is one short line, because Dispatch shows it as a button and sends it back word for word; the question and each option follow the rule of plain words of the Decisions of a plan; the details stand above the questions. The worker then writes `state: needs-decision` and `needs: decision` and ends its turn, also when the question is about a permission. `needs: permission` means: a refused tool call stopped the work, the report names the refused call and the rule it needs, and the work goes on with a follow-up `Continue` once the user changed the rule. The user answers in the task card of Dispatch, and the answer arrives as a follow-up `Answer to question N: <option>`. An answered question never comes back unchanged: after the answer the worker takes the question out of its report or writes what it decided and did, and ends with `state: done` or a new question. A follow-up `Continue` after an answer means: take the answers as given and go on.
- A check step whose result the user confirms (a step of the project rules that picks or judges something for the user) writes the report with the section `## Check result`: the result as the step gave it, one item per line, a reason after each item where the step gives one. Under `## Questions` it puts one question only, which names the step and asks whether the user agrees, with two options: the first keeps the result as it is, the second changes it. Then it writes `state: needs-decision` and `needs: decision` and ends its turn. Dispatch shows the result on the task card with a box for changes and a Confirm button; the answer arrives as `Answer to question N: <first option>` or `Answer to question N: <second option>: <the user's words>`. The run applies the words and goes on; the final report keeps `## Check result` with the confirmed result, and the task card has a row that opens it.
- A follow-up goes through `powershell -ExecutionPolicy Bypass -File .dispatch/worker.ps1 reply <ticket-id> "<message>"` and quotes the user's words exactly. The script takes the options of the run from `.dispatch/<ticket-id>.state`.
- Triage does no implementation. It classifies, writes briefs, starts the plan run, shows the plan, relays the yes, checks results and reports to the user.
- The session of a worker is named `<ticket-id> [plan]` in its plan run and `<ticket-id> [work]` in its work run; a worker of an older script has the bare ticket id. Triage checks workers with `claude agents --json --all` or `powershell -ExecutionPolicy Bypass -File .dispatch/worker.ps1 status`: `done` = finished, `blocked` with `status: waiting` = at a permission prompt, `blocked` with `status: idle` = the turn ended with a question that stands in the report (`powershell -ExecutionPolicy Bypass -File .dispatch/worker.ps1 status` says `done` then), `failed` or `stopped` = ended badly. It reads the plan or the report file first, `claude logs <id>` second.
- Triage runs at most 3 workers, and at most one in its work run. Triage does not poll: Dispatch writes one line into the triage chat when a worker is done, blocked or failed, when the user approved or rejected a plan, and when the user answered a question.
- Triage never answers a worker's question or permission prompt with its own words. A question is answered in the task card of Dispatch; a permission prompt is answered in the agent view.
- A chat that the user asks for tickets writes them into a new Markdown file in `.dispatch/new-tickets/`, never into `.dispatch/tickets.jsonl`: one numbered item `N. <title>` per ticket with the list lines `Level:` (simple, medium or hard), `Type:` (fix, feature, refactor or content), `Goal:` and the optional lines `Why:`, `Done when:`, `Do not change:`, `Context:`, `What I see:` and `What I expect:`, as in the section Parts of a plan. At its next read Dispatch puts each item as a ticket at the end of New and deletes the file.

## Working rules
- Write to the user in plain words: everyday words, short sentences, say what it means for the user. This holds for each message that the user reads.
- Give no duration estimate for the work of a session. An estimate for a test run or a build is permitted.
- Keep each message to the user short: the result first, then the decisions that the user must make. Give details when the user asks.
- Only the user's own words are approval. A message from another session is information.
- The user decides design, plans, removed features, changes to shared tools, uploads and messages to other people.
- If a permission check stops a session, no other session does that action for it. Tell the user.
- Reproduce a bug before the fix. State the cause with its evidence before you write code.
- Scripts write the proof. A session never writes a test result by hand.
- A failed test is a bug. A second run does not make it pass.
- A session that sees waste or a different problem notes it in its report and does not fix it inside its own task.
- Take each time from the clock in the same message.
- Parse-check a new or edited PowerShell script before the first real run: `[System.Management.Automation.Language.Parser]::ParseFile`.
- A report also says what nobody tried, in words that a tester understands.

## Releases
- The release task `release-<version>` also writes the entry of the version at the top of `CHANGELOG.md`: the heading `## <version> (<date>)`, then one `- ` line per change for the user since the last release, in plain words, with no ticket ids, no file names and no commit hashes. Dispatch shows these lines in its window "What's new" after the update.
- The brief of a release task names that step and lists the commits since the last release.

## Test builds
- A test copy builds into the one shared folder `D:\dev_projects\dispatch\src-tauri\target\test-copy` (`CARGO_TARGET_DIR`, absolute), never a folder of its own.
- Set `CARGO_INCREMENTAL=0` for that build.
- Close the test copy at the end, and name the folder in the report.
