# Dispatch on a laptop, work on the desktop PC

Design for ticket `remote-client`, written 2026-11-11. No code changes come with this file. Each task in "Tasks that follow" gets its own brief and plan.

The section "Several hosts" (2026-11-12, ticket `remote-multi-host`) extends the design: one window now connects to several hosts. Since then the mode "Use a host" is named "Use hosts". The section "This PC and hosts" (2026-11-12, ticket `remote-mixed-mode`) adds a third mode: the window does the work of this PC and uses hosts at the same time. The other sections keep the original design with one host.

## The problem and the result

The user wants to use Dispatch on a laptop, but the work must run on the desktop PC: the Claude Code sessions, the terminals, git and the project files. Today Dispatch does everything in one window on one PC, so the laptop can only show its own files. The result: a small host program on the desktop does the work, and the Dispatch window on the laptop (or on the desktop) connects to it over Tailscale and shows and controls it.

## How Dispatch works today

- Dispatch is one program (Tauri). The page (TypeScript in `src/`) draws the window. The backend (Rust in `src-tauri/src/`) does the work.
- The page calls the backend with `invoke`. The backend has 46 commands, all listed in `generate_handler` in `src-tauri/src/lib.rs`.
- The backend sends two events to the page: `pty-output` (new text of a terminal) and `pty-exit` (a terminal ended).
- The terminals are pseudo consoles that `portable-pty` opens inside the same program. A terminal ends when the program ends (`close_terminals`).
- The page uses four plugins: the file dialog, the system notification, the opener for links, and the window-state plugin for the window size.
- The backend reads and writes the files of the PC it runs on: the project folders, `~/.claude` (sessions, transcripts, agents), and its own data folder (`state.json`, the terminal screens, pasted images, `rules-off.json`).
- The backend runs programs on the PC it runs on: `claude`, `git`, `gh`, `curl`, PowerShell and the worker script `worker.ps1`.

Thus the split is clean at one line: everything that `invoke` reaches can run on another PC, and everything that the page does itself stays with the window.

## The split

The work moves into a new headless program, the **host** (working name `dispatch-host`). It has no window. It runs on the desktop and keeps running when every window is closed (user decision 1). The Dispatch app becomes a **window** that talks to a host, or, in the default mode, does the work itself as today.

## The transport

User decision 5: one WebSocket connection per window.

- **Calls.** A text frame carries JSON: a call id, the command name, and the arguments exactly as the page gives them to `invoke` today. The answer carries the same id and either the value or the error text. Thus the page code that calls a command does not change.
- **Events.** A text frame carries the event name and its payload, for `pty-output` and `pty-exit`.
- **Bytes.** A binary frame carries the image of `image_save` (window to host) and the bytes of `file_read` (host to window). A short header in the frame names the call id.
- **Hello.** The first message of a window carries the protocol version, the app version, the window id and the pairing key. The host answers with its own versions. A different protocol version ends the connection with a clear text, which the window shows.
- **Order.** The host keeps the order of the output of one terminal. Calls can answer out of order, as `invoke` can today.

## Finding the desktop and trusting the caller

- **Address.** The user types the desktop's MagicDNS name (`<pc>.<tailnet>.ts.net`) or its `100.x` address into the window, with a port. The port has one fixed default and can be changed.
- **Binding.** The host listens only on the desktop's Tailscale address, which it finds through `tailscale ip -4`, or else as the network interface in `100.64.0.0/10`. It never listens on all addresses (`0.0.0.0`). The desktop window reaches the same host through `127.0.0.1`; see "Open points" for this second address.
- **Pairing key.** User decision 2. The host makes a random key at its first start, stores it in its data folder, and the desktop window shows it in Options. The laptop window gets the key once and sends it in the hello. The window stores the key in its data folder, not in localStorage, because a forced end of the app loses localStorage writes. The host refuses every call before a valid hello. A "new key" button makes a new key and ends every connection that used the old one.
- **Encryption.** WireGuard already encrypts all traffic on the tailnet, so the WebSocket needs no TLS of its own.
- **Firewall.** Windows Defender Firewall asks once at the host's first listen on a network address. The user allows it for private networks.
- **Not chosen now.** The Tailscale identity through `tailscale whois` needs the Tailscale command on the desktop and a code path per system. Tailscale Serve with HTTPS and the login header needs another running configuration. Either can come later as a second check next to the key.

## The mode switch and the lifetime

The same app runs in one of two modes, chosen in Options.

| Mode | What happens |
|---|---|
| **This PC does the work** (default) | Exactly today's behaviour. The backend runs inside the app, no host starts, nothing listens on the network. |
| **Use hosts** (first "Use a host") | The window takes a list of hosts, each with a name, an address, a port and a key. It opens one WebSocket per host and sends every host call over the connection of the host that owns the pane, the project or the chat. The title bar shows the names of the hosts. |

On the desktop, Options also has **Run the host on this PC**. It starts the host, offers to start it at each Windows sign-in, shows the address and the key, and switches this window to "Use a host" with `127.0.0.1`. Thus the desktop window and the laptop window are two equal windows of one host.

Lifetime rules:

- **A terminal belongs to the window that opened it.** The host keeps the terminals of a window when that window disconnects or closes. While nobody watches, the host keeps the last 256 KB of output of each terminal. When the window connects again with the same window id, it gets that output and the terminals that are still alive, and it does not start them again. Today a start under a known terminal id ends the old shell (the check of a replaced shell in `pty_spawn`); in host mode a reconnect attaches instead.
- **A terminal that ended while nobody watched** is reported at the reconnect, as a `pty-exit`.
- **The two windows never share a pane.** Each window has its own window id, pane ids and layout. They share the projects, the chats, the tasks and the workers through the files on the desktop and the shared window state.
- **The host ends its terminals only when it stops**, as the app does today at its exit. Closing a window no longer ends the terminals of that window; closing a tab still does (`pty_kill`).
- **Workers do not depend on any of this.** They are background sessions of Claude Code, so they keep running whether the host or a window runs.

### One window drives the automatic actions

Some actions run in the page today, on a timer: the lines that Dispatch writes into the triage chat (`tellTriage` and `flushTriageQueue`), auto-approve of plans (`approvePlans`), the sending of the New tickets (`dispatchTickets`, ticket tickets and ticket auto-todo; before: the planned backlog entries), the end of old worker sessions (`autoEndStale`, ticket old-sessions-auto-end), and the compaction of the triage chat after a task (`checkCompact`, ticket triage-compact-after-task). With two windows open, both would do them: each line would reach triage twice, a plan could be approved twice, and a session could be ended twice. The host therefore gives a **driver** lease to one window at a time: the window that the user used last. Only the driver runs these actions. The other window shows the same state and runs them only when it gets the lease. The alerts (notification, chime, blink) are not part of the lease: each window alerts the person who sits at it.

## What changes for the user in client mode

| Thing | In "Use a host" mode |
|---|---|
| Paste an image | Works. The image goes from the laptop clipboard to a file in the host's `pasted` folder, and Claude Code gets that path. |
| Paste text, type, keys | Work as today. Each keystroke makes one round trip on the tailnet, so a slow network shows as typing lag. |
| Project button and focus mode folder | The native folder dialog would show the laptop's folders. A folder chooser inside the page lists the desktop's folders through `dir_list` instead. A text box for a path is in the same chooser. Local mode keeps the native dialog. |
| Links | `http` and `mailto` links open in the laptop's browser. A file link opens the viewer with the desktop's file. A file cannot open in a desktop program from the laptop. Since ticket `open-files-from-windows` the viewer has "Open in editor"; it shows only for a file of this PC, not for a file of a host. |
| Update | The laptop's Dispatch checks and installs its own update. The hello compares versions, and the status bar warns when the window and the host differ. On the desktop, an update first stops the host, because the installer cannot replace a running program, and starts it again after. |
| Notifications, chime, blink | On the laptop, for the tasks of the desktop. |
| Status bar | The Claude account and the weekly usage of the desktop. |
| Rules check, the ▶ button of a command, Setup pipeline | Run on the desktop. |
| Lost connection | A bar says that the host is not reachable, and the window tries again. Typing goes nowhere until it is back; nothing on the desktop stops. |
| Not available | The laptop cannot start the host; somebody starts it on the desktop, or it starts at sign-in. Two windows cannot show the same terminal. |

## Several hosts

Ticket `remote-multi-host`, 2026-11-12. One window connects to several hosts at once and shows the projects of all of them. The host program and its protocol did not change: a host of version 0.1.52 serves the new window.

- **The host list.** Options has the mode "Use hosts" with one row per host: Name, Address, Port, Key and Remove, and the button "Add host". Each entry has a UUID that the window makes when the user adds it; the id survives a rename and a new address. A change counts at the next start of Dispatch. "Run the host on this PC" adds or updates the row `127.0.0.1`; Stop removes it, and an empty list goes back to "This PC does the work".
- **The modes stay two** (decision 8): "This PC does the work" or "Use hosts" with one or more hosts. A window does not do work itself and use hosts at the same time. Ticket `remote-mixed-mode` changed this decision on the user's request: see "This PC and hosts".
- **The transport.** One WebSocket per entry with an address and a key, each with its own retries (1 s doubled up to 10 s), its own refusal and its own first try. Every hello carries the one window id of this window. The window-only calls stay with the window, as before.
- **Keys.** The key of a project is `<host id>|<path key>` in the mode "Use hosts" and the plain path key in the mode "This PC does the work". Each saved pane and each focus project carries its host; a saved value without a host belongs to the first host of the list.
- **Names.** With more than one host each project name gets ` · <host name>` after it: the pills, the Focus columns, the Map, the Overview cards, the chat groups and the chat tabs in the head of the triage pane. With one host nothing changes. The title is "Dispatch · host <name>" or "Dispatch · hosts <name>, <name>".
- **Lists without a project.** `chat_list` and `worker_list` are read from every host and merged, each item with its host. A host whose read fails keeps its last list.
- **Shared state per host.** Each host keeps its own `shared.json`: the Nightmode switch and the triage chat of each of its projects. The driver lease is a lease of one host, so a window can drive one host and not another.
- **The Nightmode switch.** One switch in the top bar: on when every host is on, off when every host is off, and a third look (`aria-checked="mixed"`, the knob in the middle) when they differ; the tooltip names the hosts that are on and off. A click on on turns every host off; a click on off or on the third look turns every host on. A host that is not reachable keeps its switch and is left out of the look.
- **A host that is gone.** The bar below the top bar has one row per host that is not reachable or refused the window, with its name, address and port; a refused row has Try again. The panes and projects of the other hosts keep working.
- **The status bar** follows the focused terminal: it shows the account, the usage and the versions of that terminal's host, with the host name in front when the window has more than one host. It polls every host and keeps the last values of each.
- **New terminals and projects.** The first tab at a start without saved tabs runs on the first host; a split runs on the host of the focused pane; a chat or a worker opens on its host. The folder chooser has a host list box at its top, the host of the focused pane first, hidden with one host.
- **Migration.** The old setting of one host becomes one entry named by its address. The saved focus projects, triage records, triage choices and limits, earlier triage marks, card places and focus sizes of a one-host window are copied once to the key with the host (`migrateStoredKeys`). The file of the mode "This PC does the work" keeps its format.

## This PC and hosts

Ticket `remote-mixed-mode`, 2026-11-12. The user wants to work on this desktop and see the projects of another desktop in the same window, without a host program on this desktop. The host program and its protocol did not change.

- **The mode.** Options has a third radio "This PC and hosts" under the two others. `state.json` saves the word `mixed` in the field `mode`. An older build reads an unknown word as "This PC does the work", so a downgrade keeps the local work and only drops the hosts. The host list and "Add host" count for this mode too.
- **The backends.** `local` comes first, then each host of the list with an address and a key, in the order of the list. `local` calls go to `invoke` of the app, host calls to the connection of the host. The events come from both sources at once: Tauri's `listen` for `local`, the frames for each host.
- **Keys and saved values.** The key of a project of this PC stays the plain path key, and a key of a host stays `<host id>|<path key>`. A saved pane, a focus project or a stored key without a host belongs to the first backend, which is `local` in this mode, so a file of the mode "This PC does the work" opens unchanged and `migrateStoredKeys` moves nothing.
- **Names.** This PC is named "This PC" everywhere the window names a backend: the title "Dispatch · This PC + host <name>" or "Dispatch · This PC + hosts <name>, <name>", the project names " · This PC", the status bar, the tab tooltip and the folder chooser.
- **The folder chooser.** The chooser of the page opens for every backend, "This PC" first in its list box. It lists the folders of this PC through the app command `dir_list`, the same function as the host call.
- **Shared state, lease and keep-awake.** This PC keeps its `shared.json`, its triage chats, its Nightmode switch and its power request in the app, as in the mode "This PC does the work"; each host keeps its own. A key of a host never goes to another backend. The one switch shows this PC and the hosts together. This PC always drives its automatic actions; only the hosts give a lease, and only they are read every 5 seconds.
- **Network.** Nothing on this PC listens; the window only opens connections to its hosts.
- **Run the host on this PC.** Start switches the window to "Use hosts" with the row `127.0.0.1`, also from this mode: the host then does the work of this PC, and the third mode with a host on this PC would show every project of this PC twice.

## The phone page

The ticket `i-need-an-iphone-app-with-just-overview` adds a page for a phone: the project cards of the Overview in one column, and a box for a new ticket. An icon on the Home Screen opens it. There is no App Store app.

- **The plain page on the host port.** The host looks at the head of each new connection without consuming it. A request with `Upgrade: websocket` goes on to the WebSocket service as before. Any other request gets a file: `/` and `/phone.html`, `/phone.js`, `/phone.css` and `/icon.png`. Another path gets 404, and another method gets 405. `src-tauri/build.rs` embeds the files of `dist/phone` into `dispatch-host`. The host listens on the same two addresses as before.
- **The phone key.** The host makes `phone-key.txt` in its data folder at its start. Options shows it as a code with the link `http://<tailnet address>:<port>/#key=<key>`. The page sends it in its hello with a window id that starts with `phone-`, so a phone never replaces the connection of a desktop window. After the first load the page moves the key from the fragment to the query (`/?key=<key>`), also a key that came from its storage: a Home Screen icon has its own storage and only the address that Add to Home Screen saved, and nobody has tested whether iOS keeps a fragment there. The first request of a scan still holds no key; later requests of the page do, and they reach only the user's own host over the tailnet, which gets the same key in the hello anyway. The host reads the file at each hello and at each phone call. **New phone key** writes a new file: the old key fails at its next call, and the host and its terminals keep running. The full host key keeps all its rights.
- **The PIN.** The phone key alone opens nothing (ticket `a-pin-unlocks-the-phone-page`): a connection with the phone key must enter the PIN before any other phone call works, also a direct WebSocket that does not use the page. The user sets the PIN in Options, tab Phone (at least 6 digits, nothing else); the data folder keeps `phone-pin.json` with an Argon2id hash in its PHC string (salt and parameters inside) and the count of wrong PINs, never the PIN. The one new phone call is `phone_unlock`: with `pin` the host checks the PIN and answers `{ token, typing }`; with `token` it takes a token up again after a reload; with neither it says what the phone must do. The token lives in the memory of the host, ends after 15 minutes without a call, and ends when the PIN file changes, goes or locks; the host reads the file at each phone call, so no restart is needed. Every other phone call without a live token gets `the phone must enter the PIN`, and the host drops the phone from the terminals it showed. Five wrong PINs lock the phone: the right PIN fails too until **Unlock the phone** in Options or a new PIN; `host_run_status` reports `phonePinSet` and `phonePinLocked`. `pty_write` also needs the terminal PIN: `phone_unlock` with `terminal: true` sets `typing` on the token, and `pty_leave` (Back in the Terminal view) ends it, so the phone enters the PIN once per visit of the Terminal view, also before Start terminal. The page keeps the token in `sessionStorage` (`dispatch-phone-unlock`): a reload or an app switch within 15 minutes asks no PIN, a cold start of the Home Screen app does. The page never stores the PIN, and its texts come from the host errors, which it compares word for word. The page stays plain http: Face ID or a fingerprint needs HTTPS and is a later ticket.
- **The call list.** The phone key may use `workspaces_get`, `task_list`, `worker_list`, `ticket_add` and `task_reply` (ticket `phone-version-i-need-an-option-to-see`), and `task_reject`, `task_approve_queue` and `task_approve_cancel` (ticket `approve-or-reject-a-plan-from-the-phone`), and `phone_terminal`, `pty_write` and `pty_leave` (ticket `i-need-a-terminal-access-on-mobile`). Every other call gets an error reply, and a binary frame is refused; `task_approve`, `task_decide`, `task_checks`, `task_work`, `task_stop` and `task_reply_cancel` stay closed, and so do `pty_spawn`, `pty_join`, `pty_find`, `pty_resize`, `pty_kill` and `file_read`. `phone_terminal` with `cwd` gives the running terminal with the label `project-terminal:<path key>` (the label of the Terminal switch of a window): the phone attaches to its own one or joins the one of another window, and gets its size and last output. With `start: true` and no such terminal, the host starts one with fixed arguments: shell `powershell`, the saved folder, 120 x 40, `run: "claude"`, nothing else from the phone. The reply is `{ id, cols, rows, owner, started }` or null. `pty_write` of a phone passes only for a running terminal with that label that the phone owns or joined; an unknown id is refused too. The phone never resizes or ends a terminal. The page types through a text box and key buttons; of the data of its xterm only a terminal report goes out, and only while the phone owns the terminal and the output is not a replay, as the owner window does (ConPTY waits for the answer to its cursor query at the start). The page header `Content-Security-Policy` has `style-src 'self' 'unsafe-inline'`, because xterm.js adds `<style>` elements; `script-src 'self'` stays. `task_reply` takes any text, as the desktop sends it (user decision 4 of that ticket); the worker script refuses a reply while the worker runs. A reply that the script refuses because a work folder, the same files or the branch of another task are busy is kept in `<ticket>.reply` (ticket `keep-a-reply-that-the-worker-script`): `task_list` gives it as `kept` while it answers the current report, and a desktop window queues it and sends it when the project is free; `task_reply_cancel` (Take back on the computer) removes it. `task_list`, `ticket_add`, `task_reply`, `task_reject`, `task_approve_queue`, `task_approve_cancel` and `phone_terminal` work only for a project of the project list: the host compares the whole key of `cwd` (lower case, no slash at the end) and runs the call on the saved folder. Any other `cwd`, also a subfolder or a path with `..`, gets the error `this project is not open in a Dispatch window`. `worker_list` still gives all workers of the computer, and the page keeps those of its projects. The page never calls `driver_state`, so it never takes the automatic work from a window. It reads one project at a time, at most every 10 seconds and only while it shows, because `task_list` can commit task files. The page can fold a card, hide a project, switch between Cards and Board, and open or close a column of the board for every project; these choices live in the `localStorage` key `dispatch-phone-view` of the phone, never on the host. It does not call `task_list` for a project that the phone hides.
- **The project list.** Each desktop window sends the roots of its open workspaces to each host with `workspaces_set`. A window sends a host only the projects of that host, so a project of another host never reaches it. The host keeps them by window id in `workspaces.json`; an empty list removes the window. A closed window stays in the file, so it counts again when it reconnects with its id. `workspaces_get` gives the union of the live windows: connected, with a hello or a `driver_state` report in the last 3 minutes (`WINDOW_SILENT`, because a computer that sleeps sends no close). A root that is no folder on this computer does not count. Each project shows once by its lower-case path, sorted by folder name.
- **The Board view.** The switch Cards | Board picks the view. Board shows the five columns of the tickets board per project in the order of the desktop board; In progress puts the tickets whose task waits for the user first, then those that work, then the newest. Done and Canceled show their 10 newest until Show all. An In progress ticket shows its task (joined by `ticket.task` or the id). A waiting report shows its options as buttons, a box for any reply and Send, or the confirm of a check result. Send calls `task_reply` with `Answer to question N: <option>` per question, or with the words of the box as written. The phone writes no line into a triage chat; triage learns of the answer from the next report of the worker.
- **The approval of the phone.** A plan that waits for Approve shows its block: the summary, the TL;DR lines, each decision with its options and a box for own words, the checks with the recommended ones ticked, and two pickers for the model and the effort of the work run, which start at the advice of the plan. Approve calls `task_approve_queue`: the core checks that the state is `planning` and that each decision has one answer (an option of the plan, or own words), writes `## User decisions`, `## Checks chosen` with `<ticket>.checks` and the work line of `<ticket>.models` as the desktop Approve does, then the marker `<ticket>.approved` with the line `approved: <plan millis> <iso time>`, the plan time after these writes. `task_list` gives that time as `approved` while the state is `planning` and the plan time is the same; else it removes the marker. `task_approve` removes it at the start, also when the start fails, and `task_approve_cancel` (Cancel approval on the phone or on the computer) removes it. The host never starts a work run for the phone: each desktop window takes a valid marker into its approval queue, and only the driver window starts the work run there when the project is free, under the one-work-run rule and the start lease. Reject calls `task_reject` with the reason, and the planner starts a new plan run.
- **The screens.** The page follows the mobile design of ticket `the-phone-page-follows-the-new-mobile`: a home screen and full screens, with the same data, the same calls and the same state maps. The home is Cards or Board with a fixed **New ticket** bar at the bottom in both views (user decision 1); `#app` keeps a bottom padding, so the last card clears the bar. A task row shows under its two lines what `rowAction` of `phonemodel.ts` gives: a button **Review plan**, **Answer** or **Confirm** that opens a screen, the note and **Cancel approval** of a queued approval, or the note after a send. In the Cards view the In work list draws each task as one tile instead (`tileElement`, ticket `phone-page-a-task-row-is-one-coloured`): the colour of its kind, a dot, the short line of `rowTile` and the title; a tile with a ready plan or an unsent answer is one button that opens the same screen, and the tile of a queued approval keeps **Cancel approval**. One `section.screen` holds the open screen: a head with **Back**, the title (the task, or New ticket) and the project, a scrolling body and a bottom bar with the action buttons (Send or Confirm; Approve and Reject, or Send back and Cancel while the user rejects; Add ticket). The screen keeps only the kind, the project and the mark of its row; every draw of the 10 s read rebuilds its body from `answerStates`, `planStates` and `ticketState`, and `screenRow` finds the row again by its plan or report mark over `allRows` of the cards or the boards. When the row is gone or has no block any more, the body says that the task moved on and the bar has **Done**. After a Send, Confirm, Approve, Send back or Add ticket the screen closes, and the row at home or the card note says what happened (user decision 4). The New ticket screen lists the shown projects as options and picks the project of the last ticket, else the first one (`ticketProjects`, user decision 2); `ticket_add` is the same call. The Terminal view is a `.screen` too: the head with Back and the name, the terminal in the body, the text box and the keys in the bar; `body.screen-open` hides everything else of `#app`, and the PIN form of the terminal moves into that bar. The CSS of the screens stays in the Slate colours and the system font; every button and option is at least 44 px high, and the page scrolls sideways only inside `.term-scroll`. The proof `node .dispatch/proof/the-phone-page-follows-the-new-mobile/screens.mjs [<scratch>]` builds the host into `src-tauri/target/test-copy`, starts it with the test PIN and three fixtures, and drives each screen and each action in headless Edge at 390 x 844; it writes one PNG per screen and `record.txt`.
- **More than one computer.** One page shows the projects of several hosts (ticket `the-phone-page-shows-the-projects-of`). The host the page came from is the first computer; Projects › **Add computer** takes the link of the Phone tab of another computer (`http://<address>:<port>/#key=<key>`, user decision 4) and adds it. The page opens one WebSocket per computer, each with its own key, pending calls, retry, unlock token (`sessionStorage` key `dispatch-phone-unlock:<computer id>`), round of 10 s and lists; the window id `phone-…` is the same for all. A computer id is its address in lower case. The address of the page keeps the key of the first computer as `?key=<key>` and the others as `&hosts=<address>:<port>|<key>,…`, and the `localStorage` key `dispatch-phone-hosts` keeps the same list with the names (user decision 1), so a Home Screen icon added later keeps every computer; the old key `dispatch-phone-key` is read once into that list. Each computer asks for its own PIN in a box in place of its cards, and the cards of the other computers stay (user decision 3); the PIN of the Terminal view goes to the computer of the terminal. The hello reply of the host has `name`, the computer name from `COMPUTERNAME`, else `HOSTNAME` (user decision 2); with more than one computer a card is named `<folder> · <name>`, or `<folder> · <address>` for an older host without the name. The choices of the phone are keyed by `<computer id>|<path key>`; a key without `|` belongs to the first computer, so the choices of an older page still hold. Each card takes `worker_list` of its own computer, and each call goes to the computer of its project. Remove closes the socket and takes the computer out of the address and the storage. The PIN rules, the phone key rules and the call list of each host do not change. The proof `node .dispatch/proof/the-phone-page-shows-the-projects-of/two-hosts.mjs [<scratch>]` starts two hosts on `127.0.0.1` and drives one page in headless Edge.
- **What the phone does not know.** A plan in the approval queue of a desktop window shows as waiting for Approve on the phone, and a question answered in a desktop window shows until its worker starts, because those facts live only in that window. An approval of the phone is a file of the host, so it shows as waiting for the project on the phone and in each window. An answer and a Reject from the phone show as sent only on that phone. New tickets start only while a Dispatch window drives the host.

## Open points

- **A second listen address.** The desktop window reaches the host through `127.0.0.1`, next to the Tailscale address of user decision 2. The key guards both. The alternative is that the desktop window also uses the Tailscale address, which fails when Tailscale is down on the desktop. Task 3 needs the user's yes on this.
- **One terminal in two windows.** This design does not mirror a terminal. If the user wants to continue a desktop terminal on the laptop, a later task can add a "take over" that moves a terminal to another window id.
- **A Mac as the desktop.** The host builds on macOS like the app, but the worker pipeline is Windows-only today, so a Mac host has no tasks.
- **More than one laptop, more than one host.** Several windows at one host are the design, and several hosts in one window are done (`remote-multi-host`). The proof ran two hosts on one PC; a host on a second real PC over Tailscale was not tried yet, also not in the mode "This PC and hosts".
- **Two hosts on one PC.** Both read the same `~/.claude`, so the chat list shows each chat once per host. With two real PCs this does not happen.
- **Pills in a narrow window.** With the projects of several hosts the row of pills grows, and the longer names make this happen sooner. In Focus and the Map the row scrolls sideways; in Details the pills keep their width and can lie outside a narrow top bar.
- **Night mode with a host that is gone.** The switch leaves that host out of its look and does not change it; nobody tried this by hand.
- **The Tailscale access rules (ACL) of the user's tailnet.** If they limit traffic between the two PCs, the port of the host must be allowed.
- **Install without the app.** A host without the window on a headless PC is possible with this design, but no task ships it alone.
