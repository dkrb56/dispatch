          Dispatch runs Claude Code as a team. One session, triage, takes your tasks and starts workers in the background. You give the tasks and answer the questions. The workers do the work.

          Before you start

          You need Claude Code and a project folder.

          • Install Claude Code and sign in. The command claude must start in a terminal.
          • Use a git repository for the project if you can. A folder without git also works.
          Details
          • In a git repository, Dispatch uses the top folder of the repository as the project.

          Set up a project

          Do these steps one time for each project.

          1. Click + in the projects group of the top bar. Select the folder of your project. A new project shows the Setup pipeline window.
          2. Read the steps. Each step shows "To do" or "Done". Nothing changes yet.
          3. Click Apply. Dispatch does the steps that are not done. It makes no commit.
          4. Click Commit to git. Dispatch commits the setup files.
          5. Click Close. The workspace opens: triage at the left, the workers at the right.
          6. Type your first task in the triage chat. Triage tells you when the plan is ready.
          Details
          • In the modes Use hosts and This PC and hosts, the folder chooser of Dispatch opens. With several computers, it asks for the computer too (see Where the work runs).
          • A project that is set up skips the window and opens its workspace: go to step 6.
          • The window shows its parts as tabs: Steps, Triage, Plans and work runs, Branches and checks, Files in git. A click on a tab shows that part. The window opens on Steps. Apply, Commit to git and Close stay at the bottom on every tab.
          • Click a step to see its file and the text that it adds.
          • Under the steps, the window lists the rules of the project that conflict with the pipeline, each with its file as a link. A click opens the file in the viewer, also for a rule outside the project. Open in editor there lets you change the rule yourself.
          • Apply makes no commit, so you can look at the changes in git first. When all steps are done, Commit to git becomes available.
          • Commit to git commits on the current branch: CLAUDE.md, two files in .claude (settings.json and triage.md; the allow rules in settings.local.json stay on this computer), and the script, the two options files, the measure commands and the gate command in .dispatch. With Task files local only on, it commits .gitignore instead of the files in .dispatch. With Project notes in git on, it also commits .gitignore and the notes of Claude in .claude. Your other changes stay out of the commit. Dispatch makes no push.
          • The window shows the commit, or the reason for no commit: no git repository, nothing to commit, or the error of git.
          • A work run starts only when no file of its task has uncommitted changes. The files of a task are the paths under Files to change in its plan, and the files that its task branch changed. Other uncommitted changes, the setup files among them, stay where they are and hold no task. Dispatch commits the task files in .dispatch itself, unless Task files local only is on.
          • The workspace opens below the bar with two terminals. Claude Code starts in both.
          • A close with a step still To do adds nothing. Click + again to start over.

          Details
          • Task files. Each worker writes its report and the state of its task into .dispatch. Triage writes its briefs to briefs, and each worker writes its plan to plans.
          • Task logs. Dispatch writes one log per task into logs, in the format of the illspace project: the approved plan, each command of the plan run and the work run with its exit code and its last output lines, the sections of the report as the worker wrote them, and the tokens per model. It writes the log when the plan appears, and again when the plan or the report changes. With Task files local only off, git tracks the logs with the other task files.
          • The options of the two runs are in plan-flags.txt and work-flags.txt. The lists above Workers change them. The file <ticket-id>.models of a task holds the model and the effort of its level and of its choice at Approve; they come before the lists. The script of an older version does not read that file: click Apply.
          • With Task files local only off, git tracks the folder, so a clone has the history of the tasks. Dispatch commits these files itself (the commit message starts with "Dispatch:" and names what changed and the task, for example "Dispatch: plan of overview-dot-grid"), except while a work run runs without a report. Approve does not count them as changes.
          • A project of an older version has the folder <project>-reports next to it. Apply moves its files into .dispatch and overwrites nothing. The step shows the number of files first.
          • Allow rules. Triage can run the worker script and check workers without a prompt. A deny rule keeps the approve verb of the script for the Approve button. Each session can read and write the task files in .dispatch without a prompt. The rules name the folder .dispatch relative to the project, so they work at any path.
          • Apply removes the rules of an older version that name <project>-reports. Triage can also read the job folders of the workers (%USERPROFILE%\.claude\jobs), where a worker keeps the screenshots of its visual test.
          • These rules and folders belong to your user on this computer. Apply adds the line .claude/settings.local.json with a comment line to .gitignore, so git ignores the file. When git tracked the file, Apply takes it out of git in one commit "Dispatch: the local settings stay on each computer". The file stays on the disk. A line .claude/ of your own does the same.
          • Worktree isolation off. A worker works in the project folder, not in a separate copy.
          • Section in CLAUDE.md. The section "Background workers": a task is two runs of one worker, the plan run edits nothing, your yes starts the work run as a new session that reads the brief and the plan, and the worker ends with one local commit and never pushes. Apply replaces a section with an older text. Each of the switches Start plans without decisions, Checks at the gate, Push after the merge and Tickets start their plan adds one line to the section while it is on. No triage adds one line too. Auto-merge finished tasks adds one line too.
          • Working rules. The section "Working rules": plain words, no duration estimates, only the user's words are approval, reproduce a bug before the fix, scripts write the proof, and more. Each rule has a checkbox. Apply adds the checked rules. With no checked rule, Apply adds no section.
          • Worker script. Triage runs it to start a plan run and to send your follow-ups. Dispatch runs it when you click Approve, Reject, Stop, Resume or an answer. It refuses to start the work run when a file of the task has uncommitted changes, when the worker still runs, or when the task was stopped. The worker commits only the files that it changed, each by name.
          • Measure before the plan. Off: the step is done, and nothing changes. On: the plan run may run the commands of the box under the switch, and no other command, through the worker script. The step is done when the box has a command.
          • Each command runs with cmd.exe in the project folder, one at a time in the project. It stops after 10 minutes; a first line # limit <seconds> changes that. The output and the throw-away scripts go into .dispatch/measure/<task>/, which git ignores (Apply adds measure/ to .dispatch/.gitignore). When a command changed files of the project, the task card says so.
          • Task branches. Off: the step is done, and nothing changes. On: each task works on its own branch task/<task>. Approve makes it from the branch that the project was on when the plan run started (the base). The worker commits there and never merges or pushes.
          • Checks. Dispatch reads the project folder and its direct subfolders and runs nothing: test scripts of package.json, vitest, jest, Playwright, node:test, Cargo, pytest, unittest, Go, .NET, Maven, Gradle, Makefile targets, and test files in scripts. A project without a saved list shows these tests in the box and the step Checks, and Apply saves them. Find tests adds new tests later and keeps your lines. A box that you emptied stays empty. Empty: nothing changes. With checks in the box, the plan gets a section Checks that ticks the ones it recommends for the task, and the section in CLAUDE.md says so. At Approve, Dispatch writes your choice at the end of the plan and into .dispatch/<task>.checks. The gate command of Task branches gets the path of that file as DISPATCH_CHECKS.
          • When the work run has ended and its report is written, Dispatch switches the project back to the base and commits the task files there. Then the task card shows Merge. The gate command of the box under the switch runs on the merged code first, for at most 4 hours; a first line # limit <seconds> changes that.
          • The log of the gate goes into .dispatch/merge/, which git ignores (Apply adds merge/ to .dispatch/.gitignore). The step "Allow rules" adds a deny rule, so triage cannot merge.
          • Task files in git. Off: the step is done, and nothing changes. On: Apply adds the line .dispatch/ with a comment line to .gitignore of the project, and takes the task files out of git in one commit "Dispatch: task files are local only". The files stay on the disk. Commit to git then commits .gitignore. On another computer, turn the switch on and Apply there before you pull this change, or git deletes the task files there.
          • With the switch on, tickets and task files are local only: a clone has no tickets, briefs, plans, reports or logs. Off again, Apply removes the line of Dispatch and commits the task files again. A line .dispatch/ that you wrote yourself stays.
          • Project notes in git. Off: the step is done, and nothing changes. On: git tracks the notes of Claude for the project: .claude/memory.md, mistakes.md, agents-override.md, triage.md and settings.json. When git ignores one of them, Apply adds lines under a comment line at the end of .gitignore: !.claude/, .claude/* and one ! line per file. Your own line .claude/ stays. settings.local.json and the folder .claude/state stay on this computer. Commit to git then commits .gitignore and the notes, and Dispatch commits later changes of memory.md, mistakes.md and agents-override.md with the task files.
          • Off again, Apply removes only the lines of Dispatch. The notes that git tracks stay in git. To take a file out, run git rm --cached <file>; the file stays on the disk. Commit to git then commits .gitignore.
          • Triage role. The text tells the session in the Triage terminal that it is triage: it plans and checks, and it does no implementation. The project settings change this text. Tickets start their plan adds one line: triage writes no brief for a ticket that started its own plan.

          Continue on a second computer

          Push on one computer, pull on the other, click Apply once, and go on. The other computer can use another Claude account.

          1. On the first computer, keep Task files local only off. Turn Project notes in git on when the notes of Claude shall travel too. Push the project.
          2. On the second computer, clone the project. Open the folder in Dispatch.
          3. Click Apply once. It writes the allow rules of this computer. It changes no file that git shares, so Commit to git is not necessary.
          4. Go on. The tickets, plans and reports are there. You can approve a plan and start new tasks.
          Details
          • The files that git shares name no path of your computer and no user folder. The same text works on both computers.
          • A task that ran on the other computer says "ran on another computer · no worker here" on its card. It does not block other tasks or the commits of the task files.
          • When such a task has a plan, Approve starts its work run again on this computer, from the brief and the plan. A plan run that did not finish: ask triage to start it again.
          • An answer to a question of a worker works only on the computer where the worker ran.
          • A pull brings the results of the other computer.
          • The models in the Workers bar are one choice for the project; the level of a ticket and the choice at Approve come before them. When the other account cannot use a model, the run fails with the message of Claude. Then choose another model in the Workers bar there.
          • Finish on one computer and push before you continue on the other.
          • With Task files local only on, the second computer gets the setup, but no tickets, briefs, plans, reports or logs.
          • With Project notes in git off, a clone has no notes of Claude when the project ignores the folder .claude.
          • No part of your Claude account goes into git: no login, no transcript, no email address.

          Project settings

          Switches in the Setup pipeline window for this project.

          • Short reports. Triage tells you the result and your decisions in a few lines. It gives details when you ask.
          • Fixed title. A new triage chat has the name "Triage" in the chat list.
          • Approve plans automatically. Dispatch starts the work run when a plan is ready.
          • Pause tasks. Dispatch sends no ticket and starts no work run for the project until you resume.
          • Measure before the plan. The plan run may run your commands before it writes the plan.
          • Task branches. Each task works on its own git branch.
          • Start plans without decisions. A plan that asks you nothing starts by itself.
          • Checks at the gate. Your chosen checks run once, at the merge.
          • Push after the merge. Merge also pushes your branch.
          • Auto-merge finished tasks. A task with a done report merges without your click, after the gate command passed.
          • Tickets start their plan. A New ticket starts its plan without triage.
          • No triage. The project works without a triage chat.
          • After a change, click Apply.
          • Build folders. The Setup window shows the cargo build folders of the project; Clean build folders deletes the proof builds and the incremental cache, never the main build.
          Details
          • Short reports and Fixed title are on for a new project. The other three are off. A project that was set up before stays off for Measure before the plan and Task branches.
          • A change of Short reports applies to a new triage chat only, because a chat keeps the role with which it started. The next start of the workspace (the folder button of the project, or the start of the app) opens a new triage chat.
          • Pause tasks applies at once and stays over a restart. The coloured strip above the tickets board, in the Tickets window and on the Focus board, shows the state (green "Auto-start on", yellow "Paused") and pauses or resumes with its large button. The small Pause button with the buttons of the project, in the bar and in the head of a Focus column, does the same; it shows "Paused" while the project is paused, and the pill says "paused". While paused, no ticket goes to triage, no plan starts its work run (also not with Approve plans automatically or night mode), and night mode answers no question. Your Approve click waits in line, and your answer to a question goes to the worker at once. A worker that runs finishes its run. Resume (the same button, or the strip above the tickets board) sends the next ticket and starts the next plan. While paused, Dispatch writes no ticket line by itself: the board shows the state of the tasks, and the first task read after Resume writes the changes into the tickets file. Your own moves, renames and new tickets on the board still write. A ticket that was in flight at Pause and that triage answers without a task still goes to Canceled.
          • Approve plans automatically applies at once. It waits when a file of the task has uncommitted changes or another work run runs. A change in another file does not hold it. A work run counts from the moment Dispatch starts it, so only one starts at a time, also with several plans in line. A plan with a decision marked HOLD: waits for your click. The line in the triage chat says "approved automatically".
          • Measure before the plan. Write the commands into the box under the switch: the tests, a browser test, a measuring script. The plan then has a section "Measured" with each command, what it showed and what it means. A fault that the plan run did not reproduce says "not reproduced".
          • The plan run still edits no file, starts no agent and asks you nothing. Apply changes the options of the plan run and the section in CLAUDE.md with the switch.
          • Task branches. Your branch stays clean until you merge. Approve makes the branch task/<task> from the branch that the project was on at the plan run, and the worker commits there. An answer marks the task as working before it switches the project to the task branch, so Dispatch does not switch back while the worker starts. When a worker forgot to commit its own files before it asked, Dispatch commits them on the task branch as "WIP", so your answer goes through. At each start of the worker (Approve and each answer) the task branch takes the newer commits of your branch, so a fix that you merged reaches the task. When a file changed on both sides, the task branch stays as it was, and the worker is told.
          • When the worker is done, Dispatch switches the project back to that branch. The task card then shows Merge into <branch>, until you merge the branch yourself with git.
          • Write a gate command into the box under the switch, for example your test suite. Merge runs it on the merged code and makes the merge commit only when it passes; a failed gate lists the lines of its log that say FAIL. Night mode merges a task with a done report by itself when the gate passes, and writes "Night mode merged" into the triage chat; without a gate command it does not merge. A failed gate waits for you. Nothing is pushed, unless Push after the merge is on.
          • Start plans without decisions is off at the start. On, a plan whose section Decisions has no numbered item, no list item and no HOLD: (for example only "None.") starts its work run without your click, with the recommended checks, as soon as no file of the task has uncommitted changes and no other work run runs. The plan stays readable in the task card, and the triage chat gets the line "has no decisions: Dispatch started the work run by itself". A plan with any decision waits for your click.
          • Checks at the gate is off at the start, and works only with Task branches and a gate command. On, the worker does not run the checks that you ticked, and the report check does not look for them. Your gate command runs them once, at the merge: it gets the list of the ticked checks as the file that DISPATCH_CHECKS names, one line each with the name, a tab and the command.
          • Push after the merge is off at the start, and works only with Task branches. On, Merge pushes your branch to its upstream branch after the merge commit, never with force and without a password prompt, for at most 5 minutes. The branch row of the task card then says "pushed to origin/main", "push failed" with the reason, or "no upstream branch, not pushed". A failed push leaves the merge on this computer; push it yourself. The merge of night mode pushes too.
          • Auto-merge finished tasks is off at the start, and works only with Task branches and a gate command. On, Dispatch merges a task with a done report into the branch it started from, one merge at a time, when no other work runs in the project. Each report gets one try. A failed gate or a conflict merges nothing, the reason stays on the task card, and the Merge button stays. A task waits while the checkout is on its branch or its files have uncommitted changes. Pause tasks stops the automatic merge. With Push after the merge on, an automatic merge pushes too.
          • Tickets start their plan is off at the start. Off, each New ticket goes to triage, as before. On, Dispatch writes the brief of a New ticket and starts its plan run itself (see Tickets). Apply adds one line to the section in CLAUDE.md and one to the triage role, so the next triage chat knows the step.
          • No triage is off at the start. Off, nothing changes. On, Dispatch starts the plan of every New ticket itself, also a question or a ticket with only images (see Tickets), and writes no line into a triage chat. The task cards and the alerts tell you when a plan is ready, when a worker asks, and when a task is done or failed. The workspace of the project opens with the agent view only; where triage stood, the note "No triage in this project" and a Chat button show. In Focus mode, the tickets board of the project shows there too, under the note and Chat. A triage chat that runs when you turn the switch on keeps running, but gets no lines and no tickets. Apply adds one line to the section in CLAUDE.md; the triage role stays as it is.
          • Build folders. The section shows each target folder of a cargo project with the size of its folders. debug and release are the main build and stay. Each other folder is a proof build of a worker; workers build their test copies in the one shared folder target\test-copy. The incremental folder of the main build is a cache that cargo builds again. Clean build folders deletes the proof builds and the caches, and keeps a folder in use: a target folder with a running build, or a folder with an open file, such as a test copy that still runs. A project without cargo does not show the section.

          The workspace

          The triage chat at the left, the workers at the right.

          • Triage (left). Type your tasks here. Triage plans each task with a worker and tells you when the plan is ready.
          • Approve the plan in the task card. The worker does the work, and triage reports the result.
          • A message becomes a ticket in New on the board of the project. Dispatch sends the New tickets to triage by itself, one at a time, in their order. See Tickets.
          • Chat and Terminal above Triage select its view. Chat shows formatted messages. Terminal shows Claude Code itself.
          • Workers (right). This is the agent view of Claude Code. Select a worker to see its work or answer a prompt. Back to list above it shows the list of workers again; the worker goes on working.
          • Environment in the side panel shows the shell, folder, branch and session of a terminal. Its Remote Control switch turns Remote Control on or off.
          • The yellow button in the top bar shows when a worker waits for you. Click it to open that worker.
          • A pulsing card waits for you. The pill of its project pulses too when the project is not in view. A click on the card stops it; Options and the system setting for reduced motion turn the motion off.
          • Old sessions. Dispatch ends finished worker sessions by itself after about 10 minutes. The button N old lists the ones that still wait and what Dispatch ended. End closes one now.
          • The folder button of a project opens its workspace again and continues its last triage chat.
          Details
          • For each task, triage writes a brief and starts the plan run of a worker. Dispatch writes one line into the triage chat when a worker is done, blocked or failed, and when you approved, rejected, stopped or answered in the Tasks section.
          • One triage chat per project. Dispatch never starts a second triage chat for a project whose chat runs. When another window of the same host runs it, the folder button and Start triage show that chat (see Hosts). When it runs in another program of this computer, Start triage shows a note and starts nothing.
          • Every message is a ticket, a question too. Only a message that starts with / (a command of Claude Code) goes to triage at once. For a question without a ticket, click Chat with the buttons of the project.
          • You can click Approve also while another work run edits the project or a file of the task has uncommitted changes. The card then says "Approved · waits for the project", and Dispatch starts the work run when the project is free. Until the work run starts, the task row, the card and the ticket show a blue "✓ Approved" mark. Several approved plans start one after the other: the next waits until the work run before it ends. Cancel approval takes it back.
          • A question of triage shows its options as buttons. Click one, or press Ctrl+Enter for the first.
          • In the Chat view, Enter sends the message and Ctrl+V adds an image from the clipboard. A permission prompt of triage ("Allow this read …?", "Do you want to proceed?") shows as buttons too, marked Permission.
          • Other… opens the terminal for an answer in your words. Cancel at the right end leaves a question without an answer, like Esc in Claude Code; triage then waits for your message. A permission prompt has no Cancel: use its No.
          • Use the Terminal view for a menu or a slash command.
          • Save record shows at the top right of a terminal under the mouse. When a terminal shows something wrong, such as letters that Backspace cannot remove, click it at once. It saves the last output, your last keys and the screen as a file in the folder menu-reads of the Dispatch data folder. The file stays on this computer and can hold what you typed.
          • Commands in the chat. A code block has a copy button at its top right. A one-line command also has ▶: it runs the command in a Commands terminal of the project, in the project folder, below the triage chat.
          • The Commands terminal stays for the next command. While a program still runs in it, the next command gets a second one. A command with a part in <…> goes in without Enter: fill in that part, then press Enter. The × of its bar closes it.
          • Remote Control. A click on off types /remote-control into that session, on this PC or on its host. The row says "turning on …" until Claude Code confirms; then it shows the real state again.
          • A click on on types /remote-control too and chooses Disconnect this session in the menu of Claude Code. The row says "turning off …" meanwhile. When the menu does not show as expected, Dispatch closes it with Esc and changes nothing. The switch is grey while the session works or waits for an answer.
          • Model and effort. The two lists above Triage apply at the next start of triage. Above Workers, plan sets the plan run and work the work run; they apply to the next run that triage starts. The level of a ticket sets its plan run, and the Work run row at Approve sets its work run; the lists count for a task without them.
          • Agents. A worker can start agents for parts of its task in its work run. The fifth list above Workers sets the maximum number of agents that one worker runs at the same time. A plan run starts no agent.
          • The number next to that list is the sum of the agents that the workers of the project started; it shows only when a worker started an agent.
          • N old shows when a session belongs to a finished task (done, failed or stopped), or a newer run of its task took over (Approve and each answer start a new run). It stands among the buttons of its project and counts that project only. In the Map and the Overview the top bar has N old sessions for all projects.
          • Each row of the window shows the session name, its state, why it counts as old, what Claude Code still keeps, and when it started and ended. End runs claude stop on the computer that runs the session; its conversation is kept. The task, its report and its state file do not change, and the triage chat gets no line. The card of the task then shows the run as Ended.

          Night mode

          The work goes on while you are away.

          • Turn on the Nightmode switch in the bar when you go away. It is green while night mode is on.
          • Dispatch approves plans and answers questions with their recommended option. A HOLD decision and a permission still wait for you.
          • The computer that does the work stays awake while the switch is on.
          • In the morning, Morning at the top of a column shows the defaults that night mode took.
          Details
          • The switch is the one state of night mode. The program that does the work keeps it: Dispatch in the mode This PC does the work, each host in the mode Use hosts. In the mode This PC and hosts, Dispatch keeps the switch of this PC and each host keeps its own; the one switch in the bar shows them together. So a restart brings it back as you left it, and every window of a host shows the same switch.
          • With several hosts each host has its own switch. The switch in the bar is on when every host is on, and off when every host is off. When the hosts differ, the knob stands in the middle; its tooltip names the hosts that are on and off. A click on that look turns night mode on for every host.
          • A host that is not reachable keeps its own switch and is left out of the look until it is back.
          • When this PC and a host differ, the switch reads Nightmode: mixed. The window reads the saved switch of this PC every few seconds, so a change by another Dispatch program on this PC shows too.
          • The display may turn off. When the switch goes off, or the program ends (also at a crash), the computer sleeps as before. A computer that only shows a window may sleep.
          • Keep a window open on a computer that stays awake, because the automatic actions of night mode run in a window. The window on the host's PC takes over within about 30 s when the other window sleeps. On a Mac, Dispatch runs the system tool caffeinate.
          • On and off send /nightmode start and /nightmode end and a Dispatch line to the triage chat of each project with a workspace. Triage keeps the list of the defaults and writes the morning file (your nightmode skill).
          • The triage chat follows the switch. At each start and each new triage chat, Dispatch compares the switch with the night file of the chat (.claude/state/night/night-mode.json) and sends the command again when the chat is behind. The chat never changes the switch.
          • With Push after the merge on, a merge of night mode also pushes; a failed push shows on the task card in the morning. With Start plans without decisions on, a plan without decisions starts as it does by day. With Tickets start their plan on, the New tickets start their plans at night too; with both switches on, a ticket can run to its report without a click.
          • Parts at night. A plan card with parts has the box "At night, the parts may start their work without my click". It starts unticked: then the plan of each part waits for your click at night, as a plan with a HOLD decision. Tick it, and night mode approves the plans of the parts like any plan.
          • Dispatch writes the chosen defaults into the plan, and triage hears each default. A plan with a HOLD decision and a report that needs a permission wait; triage puts them under Reminders.
          • The morning file is .claude/state/night/morning-<date>.md. Morning opens the newest one: the defaults with their options, what was built, and what waits for you.
          • A question of triage about the night defaults has View defaults in the Chat view. It opens the morning list in the viewer, and the question stays open: close the viewer, then answer or cancel. Without a morning list the button says "No morning list found".

          Where the work runs

          Do the work on this PC, or on other computers (hosts).

          • Options has three modes. This PC does the work is the default.
          • Use hosts: other computers do the work, and this window controls them.
          • This PC and hosts: this PC works, and this window controls the hosts too.

          To work from a second computer, do these steps one time.

          1. On the computer that does the work, open Options. Click Start the host in Run the host on this PC. The Key box shows the key of the host.
          2. On the other computer, open Options, select Use hosts and click Add host. A new row shows.
          3. Fill in the name, the Tailscale address and the key.
          4. Close Dispatch and start it again. The window connects to the host.
          5. Click + and select a folder of the host.
          Details
          • A change of the mode or the hosts applies at the next start of Dispatch.
          • This PC does the work: Dispatch runs the terminals, Claude Code and the workers here, and nothing listens on the network. Use hosts: the hosts run the program dispatch-host, and nothing runs on this computer. This PC and hosts: no host program runs on this computer.

Dispatch adds the row 127.0.0.1 with the name "This PC", switches this window to Use hosts and starts again. On Windows, Start the host at each Windows sign-in starts it after each sign-in.

Then your keystrokes, the terminal output, the chats, the task files, the shown files and pasted images travel.

The two programs cannot share a triage chat. Use the host switches this window to Use hosts with the row 127.0.0.1 and starts Dispatch again, as Start the host does.
