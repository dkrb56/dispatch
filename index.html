        Before you start

        You need Claude Code and a project folder.

        • Install Claude Code and sign in. The command claude must start in a terminal.
        • Use a git repository for the project if you can. A folder without git also works.
        Details
        • In a git repository, Dispatch uses the top folder of the repository as the project.

        Set up a project

        Do these steps one time for each project.

        1. Click + at the bottom of the project rail at the left edge of the window. Select the folder of your project. A new project shows the Setup pipeline window.
        2. Read the steps. Each step shows "To do" or "Done". Nothing changes yet.
        3. Click Apply. Dispatch does the steps that are not done. It makes no commit.
        4. Click Commit to git. Dispatch commits the setup files.
        5. Click Close. The workspace opens: triage at the left, the workers at the right.
        6. Type your first task in the triage chat. Triage tells you when the plan is ready.
        Details
        • In the modes Use hosts and This PC and hosts, the folder chooser of Dispatch opens. With several computers, it asks for the computer too (see Where the work runs).
        • A project that is set up skips the window and opens its workspace: go to step 6.
        • The window shows its parts in a list at the left: Steps, Plans and work runs, Branches and checks, Files in git. A click on a name shows that part. The window opens on Steps. The number next to Steps counts the steps to do, and the head of the window says how many steps are to do. Each setting is a switch on its own row, with a short text under it. Apply, Commit to git and Close stay at the bottom on every part.
        • Click a step to see its file and the text that it adds.
        • Under the steps, the window lists the rules of the project that conflict with the pipeline, each with its file as a link. A click opens the file in the viewer, also for a rule outside the project. Open in editor there lets you change the rule yourself.
        • Apply makes no commit, so you can look at the changes in git first. When all steps are done, Commit to git becomes available.
        • Commit to git commits on the current branch: CLAUDE.md, two files in .claude (settings.json and triage.md; the allow rules in settings.local.json stay on this computer), and the script, the two options files, the measure commands and the gate command in .dispatch. With Task files local only on, it commits .gitignore instead of the files in .dispatch. With Project notes in git on, it also commits .gitignore and the notes of Claude in .claude. Your other changes stay out of the commit. Dispatch makes no push.
        • The window shows the commit, or the reason for no commit: no git repository, nothing to commit, or the error of git.
        • A work run starts only when no file of its task has uncommitted changes. The files of a task are the paths under Files to change in its plan, and the files that its task branch changed. Other uncommitted changes, the setup files among them, stay where they are and hold no task. Dispatch commits the task files in .dispatch itself, unless Task files local only is on.
        • The workspace opens below the bar with two terminals. Claude Code starts in both.
        • A close with a step still To do adds nothing. Click + again to start over.

        • Task files. Each worker writes its report and the state of its task into .dispatch. Triage writes its briefs to briefs, and each worker writes its plan to plans.
        • Task logs. Dispatch writes one log per task into logs, in the format of the illspace project: the approved plan, each command of the plan run and the work run with its exit code and its last output lines, the sections of the report as the worker wrote them, and the tokens per model. It writes the log when the plan appears, and again when the plan or the report changes. With Task files local only off, git tracks the logs with the other task files.
        • The options of the two runs are in plan-flags.txt and work-flags.txt. The lists above Workers change them. The file <ticket-id>.models of a task holds the model and the effort of its level and of its choice at Approve; they come before the lists. The script of an older version does not read that file: click Apply.
        • With Task files local only off, git tracks the folder, so a clone has the history of the tasks. Dispatch commits these files itself (the commit message starts with "Dispatch:" and names what changed and the task, for example "Dispatch: plan of overview-dot-grid"), except while a work run runs without a report. Approve does not count them as changes.
        • A project of an older version has the folder <project>-reports next to it. Apply moves its files into .dispatch and overwrites nothing. The step shows the number of files first.
        • Allow rules. Triage can run the worker script and check workers without a prompt. A deny rule keeps the approve verb of the script for the Approve button. Each session can read the task files in .dispatch without a prompt. Triage can also write the briefs there. A plan run can write only its plan, and with Measure before the plan on also its measuring files. Other chats ask before they change a task file. The rules name the folder .dispatch relative to the project, so they work at any path.
        • Apply removes the rules of an older version that name <project>-reports. Triage can also read the job folders of the workers (%USERPROFILE%\.claude\jobs), where a worker keeps the screenshots of its visual test.
        • These rules and folders belong to your user on this computer. Apply adds the line .claude/settings.local.json with a comment line to .gitignore, so git ignores the file. When git tracked the file, Apply takes it out of git in one commit "Dispatch: the local settings stay on each computer". The file stays on the disk. A line .claude/ of your own does the same.
        • Worktree isolation off. A worker works in the project folder, not in a separate copy.
        • Section in CLAUDE.md. The section "Background workers": a task is two runs of one worker, the plan run edits nothing, your yes starts the work run as a new session that reads the brief and the plan, and the worker ends with one local commit and never pushes. Apply replaces a section with an older text. Each of the switches Start plans without decisions, Checks at the gate, Push after the merge and Tickets start their plan adds one line to the section while it is on. No triage adds one line too. Auto-merge finished tasks adds one line too.
        • Working rules. The section "Working rules": plain words, no duration estimates, only the user's words are approval, reproduce a bug before the fix, scripts write the proof, and more. Each rule has a checkbox. Apply adds the checked rules. With no checked rule, Apply adds no section.
        • Worker script. Triage runs it to start a plan run and to send your follow-ups. Dispatch runs it when you click Approve, Reject, Stop, Resume or an answer. It refuses to start the work run when a file of the task has uncommitted changes, when the worker still runs, or when the task was stopped. The worker commits only the files that it changed, each by name.
        • Measure before the plan. Off: the step is done, and nothing changes. On: the plan run may run the commands of the box under the switch, and no other command, through the worker script. The step is done when the box has a command.
        • Each command runs with cmd.exe in the project folder, one at a time in the project. It stops after 10 minutes; a first line # limit <seconds> changes that. The output and the throw-away scripts go into .dispatch/measure/<task>/, which git ignores (Apply adds measure/ to .dispatch/.gitignore). When a command changed files of the project, the task card says so.
        • Task branches. Off: the step is done, and nothing changes. On: each task works on its own branch task/<task>. Approve makes it from the branch that the project was on when the plan run started (the base). The worker commits there and never merges or pushes.
        • Checks. Dispatch reads the project folder and its direct subfolders and runs nothing: test scripts of package.json, vitest, jest, Playwright, node:test, Cargo, pytest, unittest, Go, .NET, Maven, Gradle, Makefile targets, and test files in scripts. A project without a saved list shows these tests in the box and the step Checks, and Apply saves them. Find tests adds new tests later and keeps your lines. A box that you emptied stays empty. Empty: nothing changes. With checks in the box, the plan gets a section Checks that ticks the ones it recommends for the task, and the section in CLAUDE.md says so. At Approve, Dispatch writes your choice at the end of the plan and into .dispatch/<task>.checks. The gate command of Task branches gets the path of that file as DISPATCH_CHECKS.
        • When the work run has ended and its report is written, Dispatch switches the project back to the base and commits the task files there. Dispatch never commits the task files on a task branch. Each switch between the base and a task branch takes them along, so no plan, report or branch file goes missing. Then the task card shows Merge. The gate command of the box under the switch runs on the merged code first, for at most 4 hours; a first line # limit <seconds> changes that.
        • The log of the gate goes into .dispatch/merge/, which git ignores (Apply adds merge/ to .dispatch/.gitignore). The step "Allow rules" adds a deny rule, so triage cannot merge.
        • Work folder. Off: the step is done, and nothing changes. On (only with Task branches): Dispatch makes the side folder .dispatch/work/1, a git worktree of the project, at the first Approve and keeps it. The set-up command of the box under the switch runs there once. Approve, an answer, Resume, Run checks and Merge then work there. Your project folder stays on your branch, and a change of yours in it holds no Approve. Apply adds work/ to .dispatch/.gitignore. With the setting "Work folders" you have 1 to 4 side folders (.dispatch/work/1 to .dispatch/work/4), and each one serves one task at a time. Setup pipeline shows how much disk space folder 1 takes under the number; each further folder costs about as much, and one first build.
        • Task files in git. Off: the step is done, and nothing changes. On: Apply adds the line .dispatch/ with a comment line to .gitignore of the project, and takes the task files out of git in one commit "Dispatch: task files are local only". The files stay on the disk. Commit to git then commits .gitignore. On another computer, turn the switch on and Apply there before you pull this change, or git deletes the task files there.
        • With the switch on, tickets and task files are local only: a clone has no tickets, briefs, plans, reports or logs. Off again, Apply removes the line of Dispatch and commits the task files again. A line .dispatch/ that you wrote yourself stays.
        • Project notes in git. Off: the step is done, and nothing changes. On: git tracks the notes of Claude for the project: .claude/memory.md, mistakes.md, agents-override.md, triage.md and settings.json. When git ignores one of them, Apply adds lines under a comment line at the end of .gitignore: !.claude/, .claude/* and one ! line per file. Your own line .claude/ stays. settings.local.json and the folder .claude/state stay on this computer. Commit to git then commits .gitignore and the notes, and Dispatch commits later changes of memory.md, mistakes.md and agents-override.md with the task files.
        • Off again, Apply removes only the lines of Dispatch. The notes that git tracks stay in git. To take a file out, run git rm --cached <file>; the file stays on the disk. Commit to git then commits .gitignore.
        • Triage role. The text tells the session in the Triage terminal that it is triage: it plans and checks, and it does no implementation. The project settings change this text. Tickets start their plan adds one line: triage writes no brief for a ticket that started its own plan.

        Continue on a second computer

        Push on one computer, pull on the other, click Apply once, and go on. The other computer can use another Claude account.

        1. On the first computer, keep Task files local only off. Turn Project notes in git on when the notes of Claude shall travel too. Push the project.
        2. On the second computer, clone the project. Open the folder in Dispatch.
        3. Click Apply once. It writes the allow rules of this computer. It changes no file that git shares, so Commit to git is not necessary.
        4. Go on. The tickets, plans and reports are there. You can approve a plan and start new tasks.
        Details
        • The files that git shares name no path of your computer and no user folder. The same text works on both computers.
        • A task that ran on the other computer says "ran on another computer · no worker here" on its card. It does not block other tasks or the commits of the task files.
        • When such a task has a plan, Approve starts its work run again on this computer, from the brief and the plan. Reject starts a new plan run on this computer; it reads the brief, the old plan and your reason. A plan run that did not finish: ask triage to start it again.
        • An answer to a question of a worker works only on the computer where the worker ran.
        • A pull brings the results of the other computer.
        • The models in the Workers bar are one choice for the project; the level of a ticket and the choice at Approve come before them. When the other account cannot use a model, the run fails with the message of Claude. Then choose another model in the Workers bar there.
        • Finish on one computer and push before you continue on the other.
        • With Task files local only on, the second computer gets the setup, but no tickets, briefs, plans, reports or logs.
        • With Project notes in git off, a clone has no notes of Claude when the project ignores the folder .claude.
        • No part of your Claude account goes into git: no login, no transcript, no email address.

        Actions

        Your own buttons for a project: a command, a Claude task, or both in a row.

        • Actions among the buttons of a project opens its panel. New action makes a button with a name and one or more steps.
        • A command step runs on the computer of the project, in the project folder. The panel shows its output and exit code. A Claude task step goes through the pipeline as a ticket: a plan, a work run, a report.
        • Approve the plan by itself on a Claude step starts the work run without your click. A plan with a HOLD decision still waits for you.
        • Run starts the first step. At the click the card hides the last run, and Run shows "Starting…" until the new run shows. The next step starts when a step ends well; the chain stops at the first step that fails.
        • Run from step N shows on a run that failed at step 2 or later. It starts the run again at the failed step; the earlier steps do not run again.
        Details
        • The files. The actions are in .dispatch/actions.json of the project, each run in .dispatch/actions/, so every window and the host show the same buttons. Each card shows the last run with its time and result; "Steps of the last run" shows each step, the ticket of a Claude task, and the last 200 lines of the output of a command.
        • Placeholders. A run fills {date} (today, UTC), {last_tag} (the last git tag), {next} (that tag with its last number plus one), {commits} (the commits since that tag) and {project} (the project folder) once at the click, in the briefs, the ticket ids and the commands. A placeholder in a command is pasted as text into the command line.
        • A Claude task gets the ticket id of its step, Working on the tickets board, and a brief whose first line says that Dispatch wrote it from the action; the triage chat does not see it. A ticket id that a ticket or a task has already fails the run. The step ends when the report says done (also after Take as done) or failed, or when you stop the task.
        • Commands. One line each; join commands with &&. Windows runs it with cmd.exe. A command stops after its time limit (one hour unless the step says other). A command runs only at your click, never at a start or on a timer. A command that ran while Dispatch ended shows as failed.
        • Pause. A paused project holds the Claude steps: the run says "held: the project is paused" and goes on at Resume. A command step runs at your click also in a paused project.
        • Run from step N. The new run shows the earlier steps with their old result and time, marked "taken from the run of …, not run again". It keeps the values of the failed run, for example {last_tag} and {next}. The steps from N on are the steps of the action now, so a fix in Edit counts. When the project got a new commit or other uncommitted changes since step N started, the panel says so first: Start anyway or Cancel. For a run from before this check, the panel says that it cannot tell. A failed Claude task step gets no button, because its ticket exists already; use Run. Run still starts at step 1.
        • The window that drives the host moves the chain on, as it approves plans. A push to GitHub happens only in an action that you click and whose command names it.
        • Release example in the editor fills in a Release: a Claude task release-{next} that sets the version and writes the changelog entry, approved by itself, then the command git tag v{next} && git push origin main v{next}. Check the texts before Save; nothing exists until then.

        Night mode

        The work goes on while you are away.

        • Each project has its own Night switch, in the tab row of a Focus column after Chats and Terminal (the Tickets window keeps its coloured strip), next to the Run queue switch. Turn it on when you go away. The switch is on while night mode is on for that project.
        • Dispatch approves plans and answers questions with their recommended option, only in the projects with night mode on. A HOLD decision and a permission still wait for you.
        • The computer that does the work stays awake while at least one of its projects has night mode on.
        • In the morning, Morning at the top of a column shows the defaults that night mode took.
        Details
        • The Night button of a project is the one state of its night mode. A click changes only that project; other projects, also those of another window or another computer, stay as they are. The program that does the work of the project keeps it: Dispatch in the mode This PC does the work, the host in the mode Use hosts, and each of them in the mode This PC and hosts. So a restart brings it back as you left it, and every window that shows the project shows the same state.
        • After the update to night mode per project, every project starts with night mode off; the old switch of a whole computer turns no project on.
        • The window reads the saved night mode of the projects of this PC every few seconds, and of each host at each poll, so a change in another window or by another Dispatch program on this PC shows too.
        • The display may turn off. When the last project of a computer turns night mode off, or the program ends (also at a crash), the computer sleeps as before. A computer that only shows a window may sleep.
        • Keep a window open on a computer that stays awake, because the automatic actions of night mode run in a window. The window on the host's PC takes over within about 30 s when the other window sleeps. On a Mac, Dispatch runs the system tool caffeinate.
        • On and off send /nightmode start and /nightmode end and a Dispatch line to the triage chat of that project, when it has a workspace. Triage keeps the list of the defaults and writes the morning file (your nightmode skill).
        • The triage chat follows the switch of its project. At each start and each new triage chat, Dispatch compares the switch with the night file of the chat (.claude/state/night/night-mode.json) and sends the command again when the chat is behind. The chat never changes the switch.
        • With Push after the merge on, a merge of night mode also pushes; a failed push shows on the task card in the morning. With Start plans without decisions on, a plan without decisions starts as it does by day. With Tickets start their plan on, the Scheduled tickets start their plans at night too; with both switches on, a ticket can run to its report without a click.
        • Parts at night. A plan card with parts has the box "At night, the parts may start their work without my click". It starts unticked: then the plan of each part waits for your click at night, as a plan with a HOLD decision. Tick it, and night mode approves the plans of the parts like any plan.
        • Dispatch writes the chosen defaults into the plan, and triage hears each default. A plan with a HOLD decision and a report that needs a permission wait; triage puts them under Reminders.
        • The morning file is .claude/state/night/morning-<date>.md. Morning opens the newest one: the defaults with their options, what was built, and what waits for you.
        • A question of triage about the night defaults has View defaults in the Chat view. It opens the morning list in the viewer, and the question stays open: close the viewer, then answer or cancel. Without a morning list the button says "No morning list found".

When they are all merged, Dispatch sends Continue by itself, day and night. When one of them cannot finish (it failed, was stopped, was canceled or does not exist), the card asks you. Go on now and Stop end the wait by hand.
        • A worker can stop at a check step and show its result, for example the test cases that a step picked with a reason each. The card then shows the result, a box for changes and Confirm. Leave the box empty to keep the result, or write what to change; Confirm sends your answer to the same work run, which goes on. The row Check result under the report row opens the result at any time later. With Confirm check results automatically on in Setup pipeline, the run does not stop at such a step, and Dispatch confirms a result that still arrives.
        • A worker that stopped at a refused step says so in its report, and the task shows Continue and Stop. Change the rule first, then click Continue. If you no longer need the task, click Stop: it asks first, and Stop now ends the task.
        • Merge. The task shows its branch, the branch it came from, and where it stands. A click merges with a merge commit after the gate command passed, and the Approve of another task waits meanwhile. A failed gate, a conflict in your code or uncommitted changes merge nothing; the card shows why. A failed gate lists the checks that failed, and a click on Gate log opens the whole log. A branch that you merge yourself with git shows as merged at the next check, with its merge commit; Merge and the old refusal go, and Dispatch deletes no branch.
        • A conflict only in the task files of .dispatch takes the version of your branch. Dispatch deletes the merged branch and writes one line into the triage chat. It makes no push. A worker that stops with a question first commits its own files on the task branch as "WIP". Uncommitted changes in other files go along with the switch back to your branch. When a file of the task has uncommitted changes, the project stays on the task branch, and the card names the file. When the task branch holds a newer report than your branch, Dispatch takes it onto your branch at the next check and commits it, so a switch of the branch never brings an old question back.
        • Stop asks first: Stop now ends the worker through the worker script, and Keep running lets it go on. Dispatch writes one line into the triage chat. The card of the stopped task then shows Resume; it lets the same worker go on where it stopped.

        Where the work runs

        Do the work on this PC, or on other computers (hosts).

        • Options has three modes. This PC does the work is the default.
        • Use hosts: other computers do the work, and this window controls them.
        • This PC and hosts: this PC works, and this window controls the hosts too.

        To work from a second computer, do these steps one time.

        1. On the computer that does the work, open Options. Click Start the host in Run the host on this PC. The Key box shows the key of the host.
        2. On the other computer, open Options, select Use hosts and click Add host. A new row shows.
        3. Fill in the name, the Tailscale address and the key.
        4. Close Dispatch and start it again. The window connects to the host.
        5. Click + and select a folder of the host.
        Details
        • A change of the mode or the hosts applies at the next start of Dispatch.
        • This PC does the work: Dispatch runs the terminals, Claude Code and the workers here, and nothing listens on the network. Use hosts: the hosts run the program dispatch-host, and nothing runs on this computer. This PC and hosts: no host program runs on this computer.
        • Start the host: the host listens on the Tailscale address of this computer and on 127.0.0.1, never on all addresses. Dispatch adds the row 127.0.0.1 with the name "This PC", switches this window to Use hosts and starts again. On Windows, Start the host at each Windows sign-in starts it after each sign-in.

        • The window connects to every host of the list. The title says "Dispatch · host <name>" with one host and "Dispatch · hosts <name>, <name>" with more. The workspace of a host folder opens on that host.
        • Several hosts. One window shows the projects of every host. With more than one host, each project name gets " · <host name>" after it, so two projects with the same folder name stay apart. With one host the names do not change.
        • This PC and hosts. This computer counts as one more computer named "This PC", first in the list. The title says "Dispatch · This PC + host <name>", and each project name gets " · This PC" or " · <host name>". The bar at the bottom names the computer of the project you click or type in, in every view, and shows its usage and versions. This PC already does its own work in this mode, so Dispatch skips the row of the host of this PC (127.0.0.1 with the key of this PC) and says so under the list. A terminal shows only under a project of its own computer.

Move to This PC opens them here and starts Dispatch again; their terminals on the host end, also a chat that runs there. Keep where they are leaves them there, and the bar does not ask again. A folder can exist on both computers, so check the list in the tooltip first.

Click a folder to go into it, or type a path and press Enter, then click Choose. With several hosts a list box at its top selects the host. In the mode This PC does the work the folder dialog of the system opens.

Typing into a terminal of the gone host goes nowhere, and nothing on that computer stops. When the host is back, a terminal that still runs there continues.

Then your keystrokes, the terminal output, the chats, the task files, the shown files and pasted images travel.

The size of that terminal follows the first window. Closing the chat in the second window leaves it running. When the first window closes, the chat keeps running on the host and the second window keeps showing it. When the chat ends, the second window shows Start triage again; one click continues the same chat.

The button opens a full screen with Back at the top and the buttons at the bottom. On the question screen tap an option and Send, or write your own reply; a check result waits for Confirm.
